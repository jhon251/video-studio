# 搜索证据质量层 —— 架构审查与最小修改设计（V2.0.x 待批）

> 审查日期：2026-08-15。状态：**已实施并验收（V2.0.1）**，实施记录见 CHANGELOG.md
> 「V2.0.1 搜索证据质量层」与 STATUS.md「第七阶段」；本文档保留为设计依据。
> **V2.0.2 修正**（见 CHANGELOG.md）：人工来源（added_by=human/manual_sources）≠ DIRECT_SUPPORT——
> support_level 必须显式评估，未标注=未评估（NULL，schema 列已改可空），fact_check 按 UNEVALUATED_MANUAL
> 保守处理；本文档中"人工来源默认直接支持"的表述以该修正为准。
> 目标：在 SearchProvider / Evidence 层解决证据质量问题，不新增 Agent。

## 一、当前架构盘点（对应代码位置）

**已存在：**
1. search→fetch→extract 严格链（fact_check._online_gather：fetch 失败/提取失败即丢弃，不直接入库）—— 满足"SearchResult ≠ Evidence"的主体约束
2. fetch 成功检查（FetchedPage.ok）、正文长度下限（_extract_from_page len<40 拒绝）
3. 关键词窗口提取（claim 关键词在正文中命中 → 窗口摘录）
4. 来源分级（_classify_host + rules.source_type_hints：official/academic/media/unknown）
5. 可靠性分级（high/medium/low；离线经 source_verify grade 映射）
6. 结论分级（Confirmed/Mostly Confirmed/Unsupported/Disputed/False）
7. 冲突检测（数值矛盾 + 可靠性差≥2，仅提示不裁决）
8. provider 回退链（baidu→bing）
9. 证据去重（同项目同 source 跳过）

**当前代码中未发现（缺失项）：**
1. 搜索结果质量预过滤（URL 有效性校验、SEO/聚合/垃圾域名黑名单、snippet 相关性预筛）
2. fetch 后"是否真的讨论 Claim"的判断（现在只查关键词是否出现——"仅包含关键词"也会通过）
3. 来源优先级排序与按 Claim 类型的首选来源规则（现按搜索排名顺序取前 3）
4. 证据支持程度分级（DIRECT/PARTIAL/CONTEXT_ONLY/CONTRADICTS/IRRELEVANT）——evidence 表无此字段
5. "搜索失败"与"没有证据"的区分记录（SEARCH_FAILED/FETCH_FAILED/NO_RELEVANT_RESULT/NO_RELIABLE_SOURCE/INSUFFICIENT_EVIDENCE）
6. 每 Claim 的搜索日志（query/provider/各阶段计数/拒绝原因）

## 二、最小修改方案（不新增 Agent，不动 V2 核心架构）

### 层 1：SearchProvider 层（代码，无 schema 变更）

1. `SearchResult` 增加 `domain` 字段；新增结果预过滤 `_prefilter(results, claim)`：
   - URL 协议校验（仅 http/https）
   - **域名黑名单/白名单**（新增 `config/search_quality.json`：聚合站/SEO 站/明显无关域黑名单；
     官方/学术/政府域优先列表）——配置化，不进代码
   - snippet 相关性预筛：claim 关键词与 title+snippet 零重叠 → 直接丢弃（记 NO_RELEVANT_RESULT）
2. `EvidenceCandidate` 增加 `support_level` 字段（代码级 dataclass 扩展）
3. `_extract_from_page` 升级为"讨论级"判断：
   - 窗口内要求 ≥2 个不同 claim 关键词，或 ≥1 个关键词 + 关键数字命中 → 通过
   - 否定语境检测（否认/辟谣/纠正/错误/not/no 邻接）→ `CONTRADICTS`
   - 关键数字缺失但主题相关 → `PARTIAL_SUPPORT`；关键词+数字齐备且无否定 → `DIRECT_SUPPORT`
   - 仅个别词出现 → `CONTEXT_ONLY`（不入库，记原因）
   - 零重叠 → `IRRELEVANT`（不入库）
4. 来源优先级排序 `_order_by_source_priority(candidates, claim_type)`：
   优先级 official/academic > regulatory/database > media > encyclopedia > forum/self-media；
   按 Claim 类型加权（论文→academic 置顶；公司/产品→official 与独立来源各取其一；
   历史→档案/权威；法律→gov/法条；医疗→学术/临床/监管）。**仅影响候选排序与
   结论加权，不改变确定性核查逻辑。**

### 层 2：fact_check 层（代码，无 schema 变更）

5. `_online_gather` 逐阶段计数并写**搜索日志**：
   - 复用 events 表（append-only，无 schema 变更）发 `SEARCH_EVIDENCE` 事件，
     payload = {claim_id, query, provider, search_results_count, relevant_count,
     fetched_count, usable_count, rejected: {reason: count}}
   - `claim_verification` 产物每条记录增加 `verification_path`（SEARCH_FAILED /
     FETCH_FAILED / NO_RELEVANT_RESULT / NO_RELIABLE_SOURCE / INSUFFICIENT_EVIDENCE /
     DIRECT_SUPPORT）+ `search_stats`
6. 结论映射（**结论词汇不变**，保持 V2.0 封版语义）：
   - ≥1 DIRECT_SUPPORT 或 ≥2 PARTIAL_SUPPORT → 现有多源/强来源逻辑 → Confirmed/Mostly Confirmed
   - 仅 PARTIAL_SUPPORT → Mostly Confirmed（弱置信）
   - 仅 CONTEXT_ONLY / IRRELEVANT → 视为无可用证据 → Unsupported，
     但 human_review_reason 区分记录（"搜索正常但无相关结果" vs "搜索失败(网络)" vs
     "无可靠来源"），不再笼统写"未找到证据"
   - CONTRADICTS → False + 人工（取代现有"【矛盾证据】"前缀约定，迁移期两者兼容）
7. 支持程度参与人工判定：只有 DIRECT/足够 PARTIAL 才能让 HIGH/CRITICAL claim 免人工；
   搜索失败类原因保持人工，但原因如实标注，便于你判断"缺资料还是搜不到"。

### 层 3：数据层（⚠ 需你批准的唯一 schema 变更）

8. `evidence` 表新增一列：
   `support_level TEXT NOT NULL DEFAULT 'DIRECT_SUPPORT'`
   - 一次性 `ALTER TABLE ... ADD COLUMN`（SQLite 附加列，向后兼容；旧行取默认值
     DIRECT_SUPPORT，保证既有测试与历史数据结论不变）
   - evidence CRUD 同步支持该字段（默认值保持兼容）
   若不批准此变更：退化为把 support_level 记入 evidence.excerpt 的 JSON 前缀——
   不推荐（脏），或仅存于产物——损失跨任务复用。

### 层 4：配置

9. 新增 `config/search_quality.json`：域名黑名单、来源优先级表、按 claim 类型的
   来源偏好、否定语境词表——全部配置化，规则变更不碰代码。

## 三、Tavily 接入方式（修改后）

- 沿用现有 `TavilySearchProvider` 槽位 + `resolve_provider`（.env 读 TAVILY_API_KEY，已就绪）
- 其 `search` 返回的 content 字段视为 provider 端已抓取的正文：`fetch()` 返回该内容
  （ok=True），并走**同一套** `_extract_from_page`（相关性/支持程度/否定检测）
- 来源优先级排序对 Tavily 结果同样生效
- 接入后无需改 fact_check/evidence/conflict 任何逻辑
