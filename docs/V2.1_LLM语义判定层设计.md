# V2.1 阶段 3 设计：LLM Semantic Judge（Rule Filter 之后的第二层判定）

> 状态：仅设计，未写代码。承接阶段 2 盲测结论（semantic_judge 纯规则在真实分布上过拟合：
> 总正确率 65.3%、DIRECT precision 22.2%、误判 CONTRADICTS 6 条含 3 条 CRITICAL）。
> 本设计引入 LLM 语义判定作为第二层，规则层降级为"过滤器 + 兜底"。
> 约束：不新增 Agent；不改变状态机；不改变结论枚举/阈值/人工闸门；不新增网络依赖。

## 一、定位与边界

```
Claim + Evidence 候选
   │
   ▼
┌─────────────────────────────┐
│ 第 1 层：Rule Filter（现状） │  关键词预筛 → fetch → 提取窗口 → 规则 support_level
└─────────────────────────────┘   （保留：廉价、确定性、零延迟、离线可用）
   │  规则层置信度：高 → 直接采用（无需 LLM）
   │  规则层置信度：低/边界 → 送第 2 层
   ▼
┌─────────────────────────────┐
│ 第 2 层：LLM Semantic Judge │  输入 Claim + 单条 Evidence
│  （fact_check 内部模块）    │  输出：五类 support_level + 一句理由（JSON）
└─────────────────────────────┘
   │
   ▼
沿用现有 fact_check 综合判据（support + reliability + 多源 + 风险闸门，全部不动）
```

- **模块归属**：`video_studio/fact_check/llm_semantic_judge.py`（或 tools 下同目录），
  由 `fact_check._online_gather` / 证据登记路径内部调用。**不注册 Agent**；
  fact_check 的 `needs_llm` 描述性改为"条件 LLM"（调度/状态机逻辑不动，见 §7）。
- **不联网**：LLM 调用**复用现有 Router**（项目既有 LLM 通道，Mock/未配置时零网络请求）；
  不引入任何外部语义服务、embedding 服务、新 SDK。未配置 LLM 时本层自动退化为规则层（现状行为）。

## 二、接口契约

```
judge_llm(claim: dict, evidence: dict, router) -> JudgeResult
JudgeResult = {
  support_level: DIRECT_SUPPORT | PARTIAL_SUPPORT | CONTEXT_ONLY | IRRELEVANT | CONTRADICTS,
  reason: str,                 # 一句中文理由（≤60 字）
  meta: {model, tier, tokens_in, tokens_out, cost_usd, latency_ms,
         cache_hit: bool, rule_label: str, llm_label: str}
}
```

- 输入 evidence 复用 Rule Filter 的输入面（title/snippet/text 窗口 ≤600 字符，截断规则不变）。
- 输出**仅五类 support_level + 一句理由**；不输出结论、不输出置信度分数、不输出裁决建议。
  结论综合仍由 fact_check 既有判据完成（DIRECT 不自动 Confirmed、CONTRADICTS 只进 Disputed+人工）。
- 结构化输出：JSON `{"support_level": "...", "reason": "..."}`；
  经 Router 既有 Schema 校验 + 五类枚举白名单校验；解析失败重试 1 次，再失败回退规则层标签。

## 三、调用时机与置信度门（谁需要 LLM）

R1 规模：50 Claim × 有效候选 108 条。全量送 LLM 约 108 次调用；本设计建议**边界筛选**：

| 规则层输出 | 是否送 LLM | 理由 |
|---|---|---|
| IRRELEVANT（0 核心命中） | 否 | 规则层高置信（阶段 2 中 IRRELEVANT precision 0.84 且误报方向多为"升支持"，不送可省 60%+ 调用） |
| CONTEXT_ONLY / PARTIAL（词面弱） | **是** | 阶段 2 主要错误区（同形词升支持/降级过度） |
| DIRECT_SUPPORT | **是** | 阶段 2 中 DIRECT precision 仅 22%，必须 LLM 复核 |
| CONTRADICTS | **是** | 阶段 2 误报率 100%（6/6），必须 LLM 复核 |
| 规则层判定 + 数字/年份/限定词冲突 | **是** | 数字与限定词是阶段 2 三类高频错误源 |

预估每轮 LLM 调用量：**约 35–50 次/轮**（而非 108 次）；其余直接采规则层标签。
（实现期可按成本预算加总开关：`llm_judge.max_calls_per_task`，默认 50，超出后剩余候选走规则层。）

## 四、Prompt 设计（要点，实现期落地）

- system：任务定义 + 五类判据（直接复述 docs/证据语义回归基准.md 的语义标准：
  同词≠支持、主体/谓词/对象/限定词、问句/定义句不可反驳、否定词辖域、无关证据不得升 DIRECT）
  + 输出 JSON 格式。
- few-shot：8–10 个示例，取自 50 样本回归集与 121 样本盲测集（各取代表性样本：
  真 DIRECT / 真 PARTIAL / CONTEXT_ONLY / IRRELEVANT / 真 CONTRADICTS / 伪 CONTRADICTS /
  关键词高重叠但无关 / 限定词缺失不得 DIRECT）。示例文本**原样引用真实样本**，不编造。
- user：`Claim: {text}\nEvidence 标题: {title}\n摘要: {snippet}\n正文窗口: {text[:600]}`。
- 参数：temperature=0（分类确定性）；tier=F（deepseek-chat）；max_tokens=256（输出只需五类+一句理由）。
- 版本：prompt 常量带 `PROMPT_VERSION`，进入缓存键（见 §5），改 prompt 即自动失效旧缓存。

## 五、缓存设计

**键**：`sha256( norm(claim_text) + "\x00" + norm(evidence.title) + "\x00" + norm(evidence.snippet) + "\x00" + norm(evidence.text[:600]) + "\x00" + PROMPT_VERSION + "\x00" + MODEL )[:32]`
（claim 与 evidence 文本均不变式证据，天然幂等；同 Claim 改文案后自动新键。）

**两级**：
- L1 内存缓存（单次 fact_check 任务生命周期，dict，容量 512，LRU）；
- L2 持久化 SQLite 新表 `llm_judge_cache`（**新增附加表，不动现有 V2 表**）：
  ```
  cache_key TEXT PRIMARY KEY, claim_id TEXT, evidence_id TEXT,
  llm_label TEXT, reason TEXT, rule_label TEXT,
  model TEXT, tier TEXT, tokens_in INTEGER, tokens_out INTEGER,
  cost_usd REAL, latency_ms INTEGER, created_at REAL
  ```
  同轮重跑/多项目同源证据/第二轮独立检索命中同一 URL → 直接命中，不再调用 LLM。

**失效**：键内含 PROMPT_VERSION 与 MODEL → 升级 prompt/模型自动失效；无 TTL（证据文本不可变）。
审计差异：缓存行同时记录 rule_label 与 llm_label，供后续 diff 分析（实现期可选）。

## 六、token 成本 / 延迟 / 缓存命中 / 降级

### 6.1 token 与成本估算（以 DeepSeek V3 定价为参考，实现期以实际账单为准）

| 项 | 冷启动/次 | 命中提示缓存/次 |
|---|---|---|
| 输入 token | ~3,400（system 350 + few-shot ~2,400 + user ~650） | ~650（few-shot/system 走上下文缓存） |
| 输出 token | ~60 | ~60 |
| 估算成本 | ~$0.0010 | ~$0.00021 |

- 单轮 108 候选全送：约 **$0.03–0.11**；边界筛选后（≈40 次）：**$0.01–0.04**。
- 落在现有 F 档预算内（F 档 budget_usd=0.05/任务）：边界筛选方案单任务约 $0.01–0.04 ✓；
  若取消边界筛选需把预算核到 M 档或提高 F 档上限（实现期确认，不改判定语义）。
- 成本回写：沿用 Router 现有成本回写（task.cost_usd / tools_used），LLM 判定成本并入 fact_check 任务。

### 6.2 延迟

- 单次调用：p50 ≈ 0.7–1.5s，p95 ≈ 3s（deepseek-chat，temperature=0）。
- 并发策略：证据间无依赖 → 实现期用线程池并发 4–6 路；每 Claim 预算 ≤3 次调用、单次超时 10s。
- 每轮增量：边界筛选 ≈40 次 → **15–40s**；缓存全命中（第二轮）→ **≈0（仅 DB 读）**。
- 缓存命中率预期：首轮 0%；第二轮独立检索（同查询、URL 复用率高，R1→R2 经验约 15–30% URL 重合）
  约 15–30%；同项目重跑 100%。

### 6.3 降级策略（顺序执行，任何一层失败都**不阻塞核查管线**）

1. LLM 未配置（无 DEEPSEEK_API_KEY / Mock 模式）→ 本层关闭，行为=现状规则层；
2. 单次调用失败/超时 → 重试 1 次 → 仍失败：采规则层标签，reason="LLM 不可用，回退规则判定"，写入审计；
3. 解析/校验失败 → 重试 1 次 → 仍失败：采规则层标签，同上；
4. 配额/限流 → 指数退避（1s/2s/4s）后放弃：剩余候选全部规则层；
5. 任务级预算护栏：`max_calls_per_task`（默认 50）与 `max_llm_ms_per_task`（默认 90s）耗尽 → 规则层兜底。
   兜底永远成立：规则层即当前系统，语义错误只会退回"现状水平"，绝不引入新失败模式。

## 七、对既有架构的影响（全部为零或可加性）

| 项 | 影响 |
|---|---|
| 状态机 / 任务流转 | 无变化（判定在 fact_check.run 内完成） |
| 结论枚举 / 综合判据 | 无变化（LLM 只产 support_level，Confirmed/Mostly/Disputed/Unsupported/False 仍由既有规则综合） |
| 人工闸门 | 无变化（CONTRADICTS→Disputed+人工、CRITICAL/HIGH 规则、无证据强制人工全部不动） |
| schema | 仅新增 `llm_judge_cache` 附加表（与 V2 新增 changelog 同类加性变更，不动现有表结构） |
| Agent 数量 | 不新增；fact_check 内部子模块 |
| 网络依赖 | 零新增（复用现有 Router；未配置 LLM 时零请求） |
| 离线/测试 | MockLLM 路径：返回固定五类之一（测试桩），缓存与回退逻辑照常可测 |
